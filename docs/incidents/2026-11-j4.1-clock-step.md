# J4.1 lost its supervision channel after a wall-clock step

## Observed on mm_m5pro, November 2026

J4.1 was a managed 16-rank VASP job. Network time was off and the wall clock
was manually advanced by approximately 28,791.6 seconds, then corrected.
The kernel boot timestamp observed by CMW changed from `1793633892.0` to
`1793662684.0`. The raw kernel start time for the protected leader stayed the
same. The original anchor birth value was `1793654971.378596`. The controller
reported `1793683763.378596` for the same PID.

The worker reported “Group leader disappeared”, recorded Unknown, closed its
anonymous control pipe and exited. The anchor survived. RELEASE requires the
write end of that particular pipe. The old runtime provides no way to recreate
it or attach a replacement worker.

A separate observation under load was recorded in guard events 109–208:
timeout and budget-exceeded samples recovered about 1–2 seconds later and
recurred about every 20–40 minutes. These events occupied the bounded guard
history. The baseline SQL prunes guard rows only, although the 30-row display
window mixes guard and lifecycle events. There is no evidence of deleted
job-lifecycle rows from that pruning.

## Mechanism and limits of the evidence

CMW v1 compared wall-clock boot time and the psutil-adjusted process creation
time exactly. On macOS psutil 7.2.2 keeps the boot time from import and adjusts
creation time by the difference from the current boot time. A fresh process
and a long-lived process can therefore disagree about the same kernel process.
The replay uses the four observed timestamps above. The recorded times demonstrate
a clock discontinuity and conflicting evidence. Neither timestamp mismatch
establishes that the kernel replaced the anchor.

The runner also checked the shared ownership predicate before draining and
signalling managed descendants. Refusal at MPI exit **if** the clock had stayed
incorrect is inferred from that code. The stored job state supplies no evidence
for scientific completion or a lost rank.
